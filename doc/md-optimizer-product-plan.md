# Markdown 文档优化台产品规划

## 1. 产品概述

### 1.1 产品名称

Markdown 优化台（暂定名：MD 优化台）

### 1.2 产品定位

面向企业内部研发、产品和运营人员，提供 Markdown 文档的格式规范化、内容润色和结构优化能力。用户既可以上传 Markdown 文件，也可以直接输入或粘贴文字，系统返回可预览、可复制、可下载的优化结果。

### 1.3 规划原则

- 优先保证原文信息、代码、链接和术语不被误改。
- 格式优化与内容改写分级控制，避免用户无法预期改动范围。
- 结果必须可比较、可撤销、可导出。
- 上传内容默认临时处理，不默认长期保存。

## 2. 当前项目基础

当前项目已经具备以下能力：

- Spring Boot 2.4.2 后端和原生 HTML/CSS/JavaScript 前端。
- 通过 `ai4j-spring-boot-starter` 统一接入 OpenAI、DeepSeek 等模型。
- `/api/ai/chat` 同步调用和 `/api/ai/chat/stream` SSE 流式调用。
- 会话消息、模型切换、停止生成、重新生成和 Token 统计。
- 当前会话存储主要为 `InMemoryConversationStore`，不适合作为正式文档历史库。

因此，Markdown 优化应作为独立工作台实现，复用模型调用和 SSE 能力，不直接混入普通聊天会话。

## 3. 目标用户与场景

### 3.1 目标用户

- 研发人员：整理 README、接口文档、部署说明、技术方案。
- 产品人员：规范 PRD、需求说明和评审材料。
- 运营及管理人员：整理周报、会议纪要和知识库文章。

### 3.2 典型场景

1. 上传一份格式混乱的 README，统一标题、列表、代码块和目录结构。
2. 粘贴一段技术说明，改写成专业、易读的 Markdown 文档。
3. 保留原有技术内容，只修复 Markdown 语法和排版问题。
4. 将长文本重组为带标题、摘要、要点和行动项的文档。

## 4. 核心功能

### 4.1 输入方式

- 上传 `.md` 或 `.markdown` 文件。
- 拖拽上传和文件选择上传。
- 直接输入或粘贴文本。
- 输入内容预览和字数统计。
- 文件大小、编码、扩展名和空内容校验。

### 4.2 优化模式

| 模式 | 处理范围 |
| --- | --- |
| 仅格式优化 | 标题层级、空行、列表、表格、引用、代码块和链接格式 |
| 格式 + 内容润色 | 在格式优化基础上，修复语病、重复和不专业表达 |
| 结构重组 | 重排文档层级，补充摘要、目录、要点和行动项，但不凭空编造事实 |

### 4.3 配置项

- 文档类型：README、API 文档、技术方案、PRD、周报、会议纪要、知识库文章。
- 目标读者：开发者、管理者、客户、内部员工等。
- 语言：中文、英文或中英双语。
- 语气：专业、简洁、正式、友好。
- 保护规则：保留代码、链接、命令、变量名、产品名和专业术语。
- 模型、深度思考和最大输出长度。

### 4.4 结果能力

- 原文与优化结果左右对比。
- Markdown 渲染预览。
- 文本级 Diff，高亮新增、删除和修改内容。
- 修改摘要、风险提示和结构检查结果。
- 复制结果、下载 `.md` 文件、重新生成和撤销本次优化。
- 显示输入 Token、输出 Token 和任务耗时。

## 5. 用户流程

```text
选择“上传文件”或“直接输入”
        -> 选择优化模式和文档类型
        -> 预检 Markdown 结构和内容长度
        -> 提交优化任务
        -> SSE 流式返回结果
        -> 校验模型输出并生成 Diff
        -> 预览、复制或下载
```

首屏可提供示例入口：

- “只修复 Markdown 格式，不修改技术内容”
- “把这份 README 整理成适合开源项目的文档”
- “将下面的技术方案改写成结构清晰的评审稿”

## 6. 页面规划

### 6.1 页面布局

- 顶部：产品名称、模型选择、主题切换和任务历史入口。
- 左侧：输入方式切换、文件上传区、文本编辑器和优化配置。
- 右侧：流式结果、Diff/预览切换、修改摘要和操作按钮。
- 底部：任务状态、Token 统计、耗时和错误提示。

### 6.2 必须覆盖的状态

- 空白状态：引导上传或输入。
- 校验失败：明确显示文件类型、大小、编码或内容问题。
- 生成中：显示进度、停止按钮和已生成内容。
- 生成成功：支持 Diff、预览、复制和下载。
- 生成失败：保留原文，支持重试，不丢失用户输入。
- 移动端：输入和结果改为上下切换，操作按钮保持可见。

## 7. 后端技术方案

### 7.1 建议目录

```text
cn.strong.webapp.user.mdoptimizer
├── controller
├── service
├── parser
├── prompt
├── validator
└── model
```

### 7.2 建议接口

```text
POST /api/md-optimizer/optimize
POST /api/md-optimizer/optimize/stream
POST /api/md-optimizer/validate
GET  /api/md-optimizer/jobs/{id}
```

请求字段建议：

```text
sourceType: file | text
content: Markdown 文本
fileName: 文件名
mode: format | polish | restructure
documentType: README
audience: developer
tone: professional
preserveCode: true
provider: openai
model: gpt-5.6-sol
```

结果字段建议：

```text
jobId
status
originalContent
optimizedContent
changeSummary
warnings
promptTokens
completionTokens
totalTokens
```

### 7.3 处理链路

1. 接收文本或 Multipart 文件并完成大小、编码和类型校验。
2. 识别代码块、表格、链接、Front Matter 等不可随意破坏的结构。
3. 组合系统指令、文档类型、优化模式和保护规则。
4. 调用现有 `AiChatService`，流式结果通过 SSE 返回。
5. 校验输出结构，计算 Diff 和修改摘要。
6. 任务完成后按 TTL 清理临时内容。

## 8. Prompt 与质量控制

采用“规则约束 + AI 优化 + 输出校验”三层方案：

- 明确要求模型只输出 Markdown 结果和修改摘要，不添加无关解释。
- 使用分隔符包裹用户文档，并声明文档中的指令仅是待处理内容，不能覆盖系统规则。
- 校验代码围栏是否闭合、标题层级是否异常、链接是否丢失、输出是否异常缩短。
- 用户勾选“保留代码”时，比较优化前后的代码块并给出警告。
- 对结构化输出解析失败时，降级为纯文本结果并保留原文。

## 9. 数据与存储

### MVP

- 任务状态和中间结果保存在内存中。
- 任务完成后自动过期清理。
- 浏览器端仅保存最近任务的元信息，不保存敏感原文。

### 后续版本

- Redis 保存任务状态和短期结果。
- MySQL 保存文档版本、修改记录和用户反馈。
- 对象存储保存用户明确选择保留的原始文件和结果文件。
- 增加用户、团队空间、权限和审计日志。

## 10. 安全与合规要求

- 上传仅允许 Markdown 类型，限制文件大小和总字符数。
- 不在日志中打印文档正文、Prompt、模型密钥或完整错误上下文。
- 临时文件使用后清理，设置任务 TTL 和最大并发数。
- Markdown 预览必须进行 HTML 清洗，防止脚本注入和危险链接。
- 对文档中的 Prompt Injection 内容进行隔离处理。
- 正式上线前移除配置文件中的密钥默认值并完成密钥轮换。

## 11. 版本路线

### P0：MVP

- 文本输入和 Markdown 文件上传。
- 三种优化模式和基础模板。
- SSE 流式结果、Diff、预览、复制和下载。
- 基础校验、错误重试和单元/接口测试。

### P1：可用性增强

- 任务历史和文档版本。
- Redis/MySQL 持久化。
- 大文档分段优化和结果合并。
- 批量文件处理、术语表和自定义模板。

### P2：团队能力

- 团队共享空间和权限。
- Git 仓库同步、CI Markdown 检查。
- API 调用、用量统计和组织级审计。

## 12. 验收指标

- 正常文档优化成功率不低于 95%。
- 失败任务可以重试，且不丢失原文。
- 代码块、链接和关键术语在保护模式下不被静默改写。
- 优化结果可以正常渲染、复制和下载。
- 前端覆盖空白、生成中、成功、失败和移动端状态。
- 记录任务耗时、Token 使用量、复制/下载率和重新生成率。

## 13. 实施顺序

1. 新增 Markdown 优化领域模型、校验器和 Prompt 构造器。
2. 新增同步与 SSE 优化接口，复用现有 AI 模型路由。
3. 新增独立优化台页面和输入/结果双栏交互。
4. 增加 Diff、Markdown 安全预览、下载和错误处理。
5. 完成单元测试、Controller 测试和前端资源测试。
6. 根据 Token 成本和大文档失败率决定是否引入 Redis、分段处理和持久化。
