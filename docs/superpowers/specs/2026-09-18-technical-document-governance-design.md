# 技术文档治理台产品设计

## 1. 定位与目标

将现有 Markdown 优化台演进为面向研发与技术团队的企业内部技术文档治理台。首期解决技术文档从编写、AI 优化、质量检查到版本沉淀的闭环，不扩展为通用 AI 工作台。

目标是使 AI 生成的建议可审阅、文档质量可解释、版本变更可追溯、团队规范可复用。

## 2. 首期范围

首期为 4 至 6 周可用版本，支持 Markdown 文档。

用户流程如下：

```text
导入或新建 Markdown
  -> 选择模板与术语库
  -> AI 优化或手动编辑
  -> 规则检查与 AI 风险提示
  -> 查看问题与版本 Diff
  -> 确认保存或发布版本
  -> 在个人或团队文档列表中检索和复用
```

| 模块 | 首期能力 | 非首期能力 |
| --- | --- | --- |
| 文档工作台 | 复用现有文本、ZIP、图片解析、优化与预览 | 多人实时协同编辑 |
| 质量检查 | 标题层级、代码块、链接、敏感占位符、术语一致性和模板必填章节 | CI 阻断 |
| 版本历史 | 自动保存草稿、手动发布、版本 Diff 和回滚 | 复杂分支合并 |
| 团队规范 | 团队术语库、文档模板和规则集 | 自定义脚本规则 |
| 文档资产 | 文档列表、标签、状态、全文检索和归档 | 外部知识库同步 |
| 基础看板 | 文档数量、检查通过率、常见问题和 AI 用量 | 成本分摊和组织级审计 |

边界：AI 只提供优化建议和风险提示；结构与术语等质量结论必须来自可解释的规则。Git、CI、知识库问答与细粒度文档 ACL 不在首期范围。

## 3. 身份、权限与数据留存

复用统一登录或网关注入的 `userId`、`teamId`、`role`，本项目不实现登录、账号密码和组织管理。

首期角色为成员和管理员：成员可创建和编辑自己的草稿，可读取团队已发布文档；管理员可管理模板、术语库、规则集及团队内文档状态。文档按团队隔离，不提供跨团队访问；细粒度文档权限顺延。

| 实体 | 核心内容 | 规则 |
| --- | --- | --- |
| 文档 | 名称、类型、标签、当前版本、状态 | 团队归属，成员可见 |
| 文档版本 | 原文、优化结果、Diff、发布说明、创建时间 | 不可变；回滚创建新版本 |
| 文档模板 | README、技术方案、接口文档、变更说明等章节结构 | 管理员维护，成员使用 |
| 术语库 | 术语、推荐写法、禁用写法、说明 | 团队共享，管理员维护 |
| 规则集 | 结构规则、模板必填项、术语规则与阈值 | 团队共享，管理员配置 |
| 质量报告 | 得分、问题、严重级别、AI 风险提示和检查版本 | 随版本生成，可重新检查 |
| 操作记录 | 保存、发布、回滚、模板与规则变更 | 只记录必要元数据 |

草稿默认保留 30 天，已发布版本长期保留。文档正文、优化结果与版本 Diff 落入业务数据库；模型密钥、完整提示词及正文不得写入应用日志或指标系统。ZIP 附件沿用浏览器端处理，首期不引入对象存储。

## 4. 服务架构

在现有 `mdoptimizer` 领域旁新增 `document-governance` 领域，复用 `AiChatService`、Markdown 解析和前端工作台，不修改普通聊天链路。

```text
统一登录网关
  -> 身份上下文（userId / teamId / role）
  -> 文档治理 API
      -> 文档与版本服务 -> MySQL
      -> 模板、术语、规则服务 -> MySQL
      -> 质量检查服务 -> 结构规则 + 术语规则 + AI 风险检查
      -> AI 优化服务 -> 复用 AiChatService
      -> 指标事件服务 -> 用量与质量聚合
```

保存草稿、发布版本和回滚都采用不可变版本记录；回滚从目标历史版本创建一个新版本。结构和术语检查同步执行，并返回带位置、严重级别、修复建议的确定性结果；AI 风险检查不阻塞保存。

AI 优化和图片解析保留现有同步能力，并增加可追踪的异步任务记录和轮询或 SSE 查询通道。模型调用、检查或保存失败时必须保留用户内容，支持重试，且不得创建半成品版本。当前阶段不启用 Redis，任务状态、幂等键与规则数据均以 MySQL 为准；后续性能瓶颈明确后再引入缓存。

## 5. 交付排期

| 周期 | 交付重点 | 验收结果 |
| --- | --- | --- |
| 第 1 周 | 身份上下文、MySQL 数据模型、文档列表和草稿 | 用户与团队数据隔离，草稿可保存和恢复 |
| 第 2 周 | 版本发布、Diff、回滚和文档状态 | 发布版本不可变，可比较任意两版并回滚 |
| 第 3 周 | 模板、术语库、确定性质量规则和报告 | 可检查章节缺失、标题层级、链接、代码块和术语违规 |
| 第 4 周 | 工作台整合、AI 风险提示、操作和用量指标 | 优化、检查、保存和发布形成单一流程 |
| 第 5 周 | 异步任务、异常重试、性能和安全验证 | AI 超时不丢稿，任务可恢复，正文不进入日志 |
| 第 6 周 | 试点反馈、规则调优和缺陷修复 | 使用真实技术文档完成试点验收 |

## 6. 验收与指标

首期试点的目标指标如下：

- 新建或修改文档中，至少 80% 完成质量检查。
- 高严重度规则问题修复率至少 70%。
- 文档保存和发布成功率至少 99%。
- 模型任务失败后可重试，且原文不丢失。
- 每份文档的模型 Token、处理耗时、规则命中和关键操作均可统计。

测试覆盖规则检查、版本不可变与回滚、团队隔离、任务重试和前端关键状态；上线前以试点团队的 README、技术方案、接口文档和变更说明进行人工验收。

## 7. 后续演进

P1 为 Git 文档治理：关联仓库、PR 和 CI，支持质量检查、质量门禁和变更说明生成。

P2 为知识资产沉淀：已发布文档进入知识库，提供语义检索、引用式问答、文档负责人和过期提醒。

P3 为组织级治理：跨团队规范继承、用量配额、审计、成本归集和合规模板。

## 8. 前置条件与风险

- 在第一周确认网关身份字段及角色映射契约。
- 确认 MySQL 的可用性、团队隔离策略和数据备份要求。
- 在试点前定义文档密级和模型调用边界，明确哪些内容不得发送给外部模型。
- 为模型调用设置成本和超时上限，并用真实文档评估质量与稳定性。
