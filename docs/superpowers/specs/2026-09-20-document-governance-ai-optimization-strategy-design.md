# 技术文档治理台 AI 优化策略可配置化设计

## 1. 背景与目标

当前技术文档治理台的 AI 优化由 `MarkdownOptimizerService` 组装固定 Prompt，用户提交文档后直接使用系统预置规则进行优化。现有 `dg_rule_set` 只负责确定性质量检查，无法表达不同团队或不同文档类型的优化重点。

本设计新增团队级“AI 优化策略集”，使管理员能够配置并发布多套优化策略，成员在文档工作台执行 AI 优化时选择策略。策略采用“结构化配置 + 自定义补充要求”，策略版本不可变，AI 任务固化实际使用的策略版本，以保证可追溯和可重试。

### 1.1 目标

- 支持团队管理员创建、编辑、发布、停用和设置默认 AI 优化策略。
- 支持成员在文档优化时选择当前团队可用的策略。
- 支持配置格式规范、结构清晰、语言表达、技术准确性、术语一致性和内容完整性等优化方向，并设置强度。
- 支持配置代码、链接、命令、变量、接口字段和专有名词等保护项。
- 支持配置新增事实、章节重排、示例补充、输出语气和模式等约束。
- 保留现有 Markdown 校验、模型调用、异步任务、SSE 状态流和结果解析能力。
- 记录实际策略版本，保证历史任务和重试行为稳定可解释。

### 1.2 非目标

- 不把 `dg_rule_set` 改造成 AI Prompt 配置表。
- 不开放脚本、DSL 或自定义执行器。
- 不实现多人实时协同、Git/CI 门禁或知识库同步。
- 不在本期引入新的消息队列、缓存或独立微服务。

## 2. 现状与约束

当前实现边界：

- `DocumentGovernanceController` 提供文档、质量检查和 AI 任务接口。
- `DocumentAiTaskService` 负责任务幂等、异步执行、SSE 状态通知和失败重试。
- `MarkdownOptimizerService` 负责 Markdown 校验、Prompt 组装、模型调用和结果解析。
- `RuleSetService` 与 `RuleConfig` 负责确定性质量规则的启用、严重级别和扣分权重。
- `dg_ai_task` 已记录 provider、model、Token 和状态，但没有记录优化策略。
- 团队身份由现有 `DocumentIdentityResolver` 提供，系统不实现登录和组织管理。

设计约束：

- 采用现有模块化单体结构，在 `documentgovernance` 领域增加策略模块。
- 继续使用 MySQL 作为配置、任务和版本事实来源。
- 不改变现有质量检查规则的职责和接口语义。
- 兼容没有策略字段的历史 AI 任务。
- 正文、完整 Prompt、模型密钥和完整自定义指令不得写入日志或指标系统。

## 3. 方案对比与选型

### 3.1 方案 A：扩展现有 `dg_rule_set`

将 AI 优化字段直接加入 `config_json`。

- 优点：表结构和管理接口改动少。
- 缺点：确定性质量检查与 AI Prompt 配置职责混杂，版本发布、权限和审计边界不清晰，后续难以独立演进。

### 3.2 方案 B：新增独立 AI 优化策略集（采用）

新增策略主表和不可变版本表，质量规则集继续只负责质量检查；AI 任务引用策略版本，由编译器生成 Prompt。

- 优点：职责清晰，支持多策略、版本化、发布回滚、历史追溯和独立权限。
- 缺点：新增表、接口、管理页面和迁移工作。

### 3.3 方案 C：通用规则引擎

将优化方向建模为可编排节点或脚本。

- 优点：理论扩展性最高。
- 缺点：引入 DSL、运行时安全、调试和运维复杂度，超出当前需求。

采用方案 B，以结构化字段覆盖当前可预期的优化重点，不开放脚本执行。

## 4. 总体架构

```text
管理端
  -> AI 优化策略 API
      -> 策略主表 / 策略版本表
      -> 草稿、发布、停用、默认、复制
            |
文档工作台
  -> 选择策略集
  -> 提交 AI 优化任务
      -> 固化 strategyVersionId
      -> 加载不可变策略快照
      -> AiOptimizationStrategyCompiler
      -> MarkdownOptimizerService
      -> AiChatService
      -> 应用优化结果到草稿
```

### 4.1 组件职责

#### `AiOptimizationStrategyService`

- 创建策略集和初始草稿版本。
- 查询当前团队策略及已发布版本。
- 创建新版本、发布版本、设置默认、停用策略。
- 校验团队归属、管理员权限和版本状态。
- 通过事务保证发布和默认策略切换的一致性。

#### `AiOptimizationStrategyCompiler`

- 将结构化策略转换为稳定的系统 Prompt 片段。
- 应用默认值并校验方向、强度、保护项和输出约束。
- 固定系统安全约束和输出协议。
- 隔离自定义补充要求，确保其优先级低于系统安全约束和结构化约束。
- 计算规范化配置哈希，供任务追踪和幂等分析使用。

#### `DocumentAiTaskService`

- 提交任务时解析默认策略或指定策略。
- 将 `strategyId`、`strategyVersionId` 和配置哈希固化到任务。
- 异步执行时仅使用任务关联的不可变版本。
- 重试沿用原策略版本，不重新读取当前默认策略。

#### `MarkdownOptimizerService`

- 保留现有 Markdown 校验、模型调用和结果解析。
- 新增可选的已编译优化上下文，不改变普通 Markdown 优化接口的默认行为。

#### 现有质量检查模块

`RuleSetService`、`RuleConfig`、`MarkdownQualityChecker` 和质量报告接口继续只处理确定性质量规则。AI 优化策略不得写入 `dg_rule_set`。

## 5. 核心数据流

### 5.1 管理员发布策略

1. 管理员创建策略集，系统生成版本 1 草稿。
2. 管理员修改结构化配置或自定义要求，保存为草稿版本。
3. 服务端严格校验配置，生成规范化 JSON 和 `config_hash`。
4. 管理员发布版本；发布版本不可修改，只能基于它复制出新草稿。
5. 如设置为默认策略，在同一事务中取消团队原默认策略并设置新默认策略。
6. 写入操作日志，记录策略 ID、版本号和操作类型，不记录完整指令。

### 5.2 成员执行 AI 优化

1. 工作台加载当前团队启用且有已发布版本的策略列表。
2. 默认选中团队默认策略；没有团队默认策略时显示系统默认兼容策略。
3. 请求携带可选 `strategyId`，后端校验当前团队归属、启用状态和已发布版本。
4. 创建任务时保存 `strategy_id`、`strategy_version_id` 和 `strategy_config_hash`。
5. 异步执行时读取不可变策略版本，编译 Prompt 并调用现有模型链路。
6. 成功后只更新文档草稿，不自动发布版本和触发质量检查。
7. 结果校验失败、模型超时或调用失败时，任务失败且原草稿保持不变。
8. 任务状态、策略版本和结果摘要通过现有查询/SSE 接口返回。

策略中的 `provider`、`model`、`deepThinking` 和 `maxTokens` 必须完整映射到现有 `MarkdownOptimizeRequest`/`AiChatRequest`；不能只传 provider 和 model，否则策略配置的模型参数不会生效。

## 6. 数据模型设计

### 6.1 策略主表：`dg_ai_optimization_strategy`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `team_id` | VARCHAR(64) | 团队 ID |
| `name` | VARCHAR(100) | 策略名称 |
| `description` | VARCHAR(500) | 策略说明 |
| `status` | VARCHAR(16) | `ENABLED` / `DISABLED` |
| `current_version_id` | BIGINT | 当前发布版本，可为空 |
| `is_default` | TINYINT(1) | 是否团队默认策略 |
| `created_by` | VARCHAR(64) | 创建人 |
| `created_at` | BIGINT | 创建时间（毫秒） |
| `updated_at` | BIGINT | 更新时间（毫秒） |

约束：

- `UNIQUE(team_id, name)`。
- `INDEX(team_id, status)`。
- 同一团队只能有一个默认策略，由事务内校验和数据库约束策略保证。

### 6.2 策略版本表：`dg_ai_optimization_strategy_version`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `strategy_id` | BIGINT | 策略主表 ID |
| `version_no` | BIGINT | 策略版本号 |
| `status` | VARCHAR(16) | `DRAFT` / `PUBLISHED` |
| `config_json` | TEXT | 规范化后的策略配置 |
| `config_hash` | VARCHAR(64) | SHA-256 或等价稳定哈希 |
| `created_by` | VARCHAR(64) | 创建人 |
| `created_at` | BIGINT | 创建时间（毫秒） |
| `published_at` | BIGINT | 发布时间（毫秒） |

约束：

- `UNIQUE(strategy_id, version_no)`。
- 已发布版本不可更新配置；基于历史版本复制生成新草稿。
- `INDEX(strategy_id, status)`。

### 6.3 AI 任务字段扩展

在 `dg_ai_task` 增加以下可空字段：

- `strategy_id BIGINT`：提交时选择的策略主表 ID；系统默认兼容策略可为空。
- `strategy_version_id BIGINT`：实际执行的策略版本 ID。
- `strategy_config_hash VARCHAR(64)`：执行时配置哈希。

历史任务字段为空时，按系统默认兼容策略解释，不强制回填。

### 6.4 策略配置 JSON

```json
{
  "directions": {
    "format": {"enabled": true, "intensity": "medium"},
    "structure": {"enabled": true, "intensity": "high"},
    "language": {"enabled": true, "intensity": "medium"},
    "technicalAccuracy": {"enabled": true, "intensity": "high"},
    "terminology": {"enabled": true, "intensity": "medium"},
    "completeness": {"enabled": false, "intensity": "low"}
  },
  "protections": {
    "codeBlocks": true,
    "links": true,
    "commands": true,
    "variables": true,
    "apiFields": true,
    "properNouns": true
  },
  "constraints": {
    "allowNewFacts": false,
    "allowSectionReorder": false,
    "allowExamples": false,
    "tone": "专业、简洁",
    "mode": "format"
  },
  "customInstruction": "",
  "model": {
    "provider": "openai",
    "name": "gpt-5.6-sol",
    "deepThinking": false,
    "maxTokens": 8192
  }
}
```

字段规则：

- 方向编码固定为 `format`、`structure`、`language`、`technicalAccuracy`、`terminology`、`completeness`。
- 强度固定为 `low`、`medium`、`high`。
- `customInstruction` 最大 2,000 个字符。
- `mode` 复用现有 `format`、`polish`、`restructure` 枚举。
- 模型 provider/model 复用现有白名单校验。
- 严格反序列化，拒绝未知字段和非法枚举值。

## 7. API 设计

### 7.1 策略管理接口

接口统一挂载在 `/api/document-governance/ai-strategies` 下：

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| GET | `/` | 查询当前团队策略 | 成员 |
| POST | `/` | 创建策略和初始草稿版本 | 管理员 |
| PUT | `/{id}` | 修改策略名称和描述 | 管理员 |
| POST | `/{id}/versions` | 创建新草稿版本 | 管理员 |
| GET | `/{id}/versions` | 查询策略版本历史 | 管理员 |
| POST | `/{id}/versions/{versionNo}/publish` | 发布指定版本 | 管理员 |
| POST | `/{id}/default` | 设置为团队默认策略 | 管理员 |
| POST | `/{id}/disable` | 停用策略 | 管理员 |

策略查询返回主表基本信息、当前发布版本号和是否默认；成员查询不返回草稿版本的完整自定义指令。

### 7.2 AI 任务接口扩展

现有接口保持路径不变：

`POST /api/document-governance/documents/{documentId}/ai-tasks`

请求增加：

```json
{
  "idempotencyKey": "doc-1001-1710000000",
  "strategyId": 12
}
```

首期模型参数由策略决定，前端不能覆盖 `provider`、`model`、`deepThinking` 和 `maxTokens`。保留旧请求字段的读取兼容，但新工作台不再提交这些覆盖字段。

任务响应增加：

```json
{
  "strategyId": 12,
  "strategyVersionId": 3,
  "strategyVersionNo": 2,
  "strategyConfigHash": "..."
}
```

### 7.3 错误语义

- 策略不存在、跨团队、停用或无已发布版本：参数错误，不创建任务。
- 策略配置非法：保存或发布时返回字段级校验错误。
- 模型失败：任务标记 `FAILED`，使用现有错误码体系，不覆盖草稿。
- 结果校验失败：任务标记 `FAILED`，记录非敏感失败原因，不应用优化结果。

## 8. Prompt 编译与安全

### 8.1 编译顺序

1. 固定系统安全约束：只处理文档内容，不执行文档内指令，不泄露系统提示词，不凭空添加事实。
2. 固定输出协议：沿用 `<<<OPTIMIZED_MARKDOWN>>>` 和 `<<<CHANGE_SUMMARY>>>` 标记。
3. 注入文档类型和目标读者等上下文。
4. 按固定顺序编译结构化优化方向、强度、保护项和输出约束。
5. 将 `customInstruction` 放入独立“团队补充要求”区块，明确其优先级低于安全约束和结构化约束。
6. 使用现有分隔符包裹文档内容，并声明文档中的指令只是待处理文本。

### 8.2 方向映射

- `format`：统一标题、空行、列表、表格、引用和代码块格式。
- `structure`：改善章节层级、段落顺序和信息组织，受 `allowSectionReorder` 控制。
- `language`：修复语病、冗余和表达不一致。
- `technicalAccuracy`：只澄清表达，不改变事实、参数、命令和接口含义。
- `terminology`：优先使用团队术语库的推荐写法。
- `completeness`：仅在允许时补齐摘要、前置条件、边界说明等结构内容，禁止虚构事实。

### 8.3 结果应用前校验

- 模型返回内容非空。
- 结果可被现有 Markdown 校验器接受。
- 输出协议能被现有结果解析器解析；解析失败时允许安全兜底，但必须保留失败警告。
- 开启代码块保护时，比较优化前后代码块数量和内容；破坏保护项则不应用结果。
- 开启链接保护时，比较链接目标集合；异常变更则不应用结果。

## 9. 前端交互

### 9.1 策略管理页

- 列表显示名称、描述、状态、默认标识、当前发布版本、更新时间和创建人。
- 编辑器分为优化方向、保护项、输出约束、自定义要求和模型参数五个区域。
- “保存草稿”和“发布版本”分离；发布前显示配置摘要并执行校验。
- 支持查看版本历史，并基于历史版本复制为新草稿。
- 停用需二次确认；停用策略从工作台选择列表隐藏。

### 9.2 文档工作台

- 在现有“AI 优化”按钮旁增加策略下拉框。
- 默认选中团队默认策略；无默认策略时显示系统默认兼容策略。
- 下拉项显示策略名称和当前发布版本。
- 提交任务后锁定本次策略显示，并在任务结果摘要中展示策略版本。
- 重试沿用任务原策略版本，不受当前下拉框变化影响。
- 移动端将策略选择折叠到现有优化设置区域。

## 10. 权限、审计与数据安全

### 10.1 权限

- 成员：读取可用策略，在自己可编辑的文档上选择策略执行优化。
- 管理员：创建、编辑、发布、设置默认、停用和查看版本。
- 所有查询和写入使用现有 `teamId` 做租户隔离。

### 10.2 审计

复用 `dg_operation_log`，记录以下操作：

- `AI_STRATEGY_CREATED`
- `AI_STRATEGY_UPDATED`
- `AI_STRATEGY_VERSION_CREATED`
- `AI_STRATEGY_VERSION_PUBLISHED`
- `AI_STRATEGY_DEFAULT_CHANGED`
- `AI_STRATEGY_DISABLED`

元数据只包含策略 ID、版本号和必要的变更摘要，不记录完整自定义指令、正文或完整 Prompt。

### 10.3 数据安全

- 自定义要求按不可信输入处理，不能覆盖系统安全约束。
- Prompt 不写入应用日志、操作日志和指标标签。
- 正文仅沿用现有业务数据存储链路，模型密钥不进入策略配置。
- 策略配置和任务响应不得跨团队读取。

## 11. 兼容、迁移与失败处理

### 11.1 默认策略兼容

- 为现有团队提供“系统默认兼容策略”，行为等价于当前固定 Prompt。
- `strategyId` 为空时优先使用团队默认策略；团队没有默认策略时使用内置兼容策略。
- 历史 AI 任务策略字段为空时按兼容策略解释，无需回填。

### 11.2 数据库迁移

- 新增一份 Flyway migration，创建两张策略表。
- 在 `dg_ai_task` 增加三个可空字段和索引。
- 不修改已有字段含义，不删除历史数据。
- 同步更新 `doc/sql/document-governance-mysql.sql`，确保手工建库脚本与迁移一致。

### 11.3 失败处理

| 场景 | 处理 |
| --- | --- |
| 策略不存在、跨团队、停用 | 创建任务前拒绝 |
| 策略没有已发布版本 | 创建任务前拒绝 |
| 保存或发布时配置非法 | 返回字段级错误 |
| 模型超时或不可用 | `FAILED`，原草稿不变，可按原策略版本重试 |
| Prompt 或结果校验失败 | `FAILED`，不应用结果 |
| 管理员发布新版本 | 只影响后续新任务 |
| 策略服务读取异常 | 不执行优化；只有明确无团队策略时才回退兼容策略 |

## 12. 非功能要求

### 性能

- 策略列表和详情接口 p95 不超过 300ms。
- Prompt 编译只使用本地配置和内存计算，不新增外部网络调用。

### 一致性

- 发布版本、设置默认策略和停用策略使用事务。
- 通过唯一约束或事务内校验保证同一团队只有一个默认策略。
- 任务创建时固化版本，运行期间不读取可变的当前版本指针。

### 可观测性

- 记录策略 ID、版本号、配置哈希、模型、处理耗时、Token 和成功/失败状态。
- 指标标签禁止包含正文、自定义指令和完整 Prompt。

### 可维护性

- 方向编码、强度枚举、配置 schema、默认策略和 Prompt 编译规则集中管理。
- 前端只负责编辑合法字段，不自行拼接 Prompt 或复制后端默认规则。

## 13. 测试与验收

### 13.1 单元测试

- 配置默认值、枚举校验、未知字段、长度限制和稳定哈希。
- Prompt 编译的方向映射、强度、保护项、约束和自定义要求隔离。
- 结果校验对空结果、非法 Markdown、代码块和链接变更的处理。

### 13.2 服务与接口测试

- 团队隔离和管理员权限。
- 版本不可变、发布、停用、默认切换和并发发布。
- 默认策略、显式策略、无策略兼容回退和重试使用原版本。
- 停用策略拒绝新任务但不影响历史任务读取。

### 13.3 数据迁移与回归测试

- 新库初始化和既有库升级。
- 旧 `dg_ai_task` 数据读取。
- 现有质量检查、普通 Markdown 优化、版本发布/回滚和团队隔离回归。
- 前端策略加载、默认选中、提交参数、任务锁定和失败状态。

### 13.4 验收标准

- 管理员可以创建并发布至少两套不同重点的策略。
- 成员可以在同一篇文档中切换策略，并观察到符合配置方向的差异化优化结果。
- 任务详情准确显示实际策略版本和配置哈希。
- 发布新版本后，旧任务重试仍使用旧版本。
- 配置错误、模型失败和结果校验失败均不会丢失原草稿。
- 未选择策略时的行为与改造前一致。

## 15. 关键架构决策记录

### ADR-001：AI 策略与质量规则分离

- **背景**：质量规则已有 `dg_rule_set`，AI 优化需要配置重点方向和 Prompt 约束。
- **决策**：新增独立 AI 优化策略集，不扩展 `dg_rule_set` 的职责。
- **原因**：避免领域耦合，支持独立版本、权限、发布和审计。
- **代价**：新增表、接口和管理功能。

### ADR-002：任务固化策略版本

- **背景**：管理员可能在任务执行期间发布新策略版本。
- **决策**：任务创建时保存策略版本 ID 和配置哈希，执行和重试均使用该版本。
- **原因**：保证结果可解释、重试稳定和历史可追溯。
- **代价**：任务表增加字段，策略版本需要长期保留。

### ADR-003：结构化配置优先，不开放脚本

- **背景**：不同团队需要不同优化重点，但当前规模不需要通用编排平台。
- **决策**：首期只支持固定方向、强度、保护项、约束和自定义补充要求。
- **原因**：降低安全风险和运维复杂度，保留后续扩展空间。
- **代价**：暂不支持团队自定义算法或复杂条件分支。

## 16. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 自定义要求诱导模型绕过约束 | 生成不安全或不符合预期的内容 | 固定安全约束优先级，长度限制，结果校验 |
| 策略方向对模型效果影响不稳定 | 用户难以判断配置价值 | 记录版本和指标，以真实文档灰度评估，提供兼容默认策略 |
| 发布与任务执行并发 | 任务使用错误配置 | 任务固化版本，不读取可变当前版本 |
| 配置模型持续膨胀 | 前后端维护困难 | 集中 schema，新增字段需版本化并保持向后兼容 |
| 结果保护校验误报 | 合法优化被拒绝 | 首期只校验代码块和链接等高风险保护项，提供失败原因 |
| 策略数据跨团队访问 | 数据泄露 | 所有查询按 `teamId` 过滤，并覆盖服务和接口测试 |
