# 首页对话图片输入设计

- 日期：2026-10-10
- 状态：设计方案，尚未实施
- 页面：`strong-ai-webapp/src/main/resources/static/index.html`
- 核心方案：独立上传图片，聊天消息提交附件 ID，后端组装多模态请求，继续使用现有 SSE 流式输出。

## 1. 目标与范围

在首页对话框增加图片输入，支持图文问答、纯图片问答、历史回显、连续追问和重新生成，保持现有纯文本聊天兼容。

一期范围：

| 项目 | 设计 |
| --- | --- |
| 输入方式 | 文件选择、截图粘贴、拖拽图片 |
| 消息形式 | 纯文本、文字加图片、纯图片 |
| 数量限制 | 每条消息最多一张图片，接口使用列表预留多图扩展 |
| 大小限制 | 单张最大 10 MB |
| 图片格式 | PNG、JPEG、WebP |
| 历史能力 | 刷新后回显图片，追问和重新生成包含相应历史图片 |
| 回复形式 | 沿用文字和 Markdown 回复 |

不在一期范围内：图片生成、多图输入、GIF 动图、SVG、PDF、任意外部图片 URL、对象存储服务接入。

纯图片发送时，消息的 `content` 可以为空。后端调用模型时补充默认问题“请描述并分析这张图片”，不将其作为用户原始输入保存。

## 2. 现有实现与约束

- `index.html` 的输入区域目前只有文本框、模型标识、深度思考和发送按钮。
- `app.js` 的 `handleSubmit()`、`updateComposer()` 只允许非空文本发送，聊天请求为 `{ content }`。
- `ConversationChatRequest`、`ConversationMessage` 和 `AiChatMessageRequest` 当前仅表达文本内容。
- `ConversationService.prepareChatRequest()` 拒绝空文本；`toChatRequest()` 只组装文本历史且会过滤空文本消息，需要支持纯图片消息。
- `AiChatService.chatWithImage()` 已具备同步单轮图片调用方式，但不能直接替代现有会话流式链路。
- `MysqlConversationStore.save()` 在事务内删除并重新插入该会话的全部消息，附件不能依赖消息删除级联清理。
- 项目同时支持 MySQL 和内存会话存储，需要让两种模式都支持附件。
- 当前会话模型没有用户归属字段；校验附件属于会话，不等于完成用户级授权。

## 3. 架构与组件

```text
选择图片 → 本地校验和预览 → 点击发送 → 上传附件
    → 获取 attachmentId → 提交 content + attachmentIds
    → 校验附件、保存用户消息并绑定附件
    → 加载图文历史 → 组装多模态请求
    → 模型调用 → SSE 回复 → 保存助手消息
```

| 组件 | 职责 |
| --- | --- |
| 前端附件状态 | 管理文件、预览、上传状态和会话草稿 |
| ConversationAttachmentController | 提供上传、读取、删除未发送附件接口 |
| ConversationAttachmentService | 文件校验、附件归属、绑定和过期清理 |
| ConversationAttachmentStore | 附件元信息及图片内容存储 |
| ConversationService | 图文消息、历史上下文和事务组织 |
| AiChatService | 多模态消息转换和现有流式模型调用 |

图片内容与聊天文本分开管理。前端只提交附件 ID，不负责构造上游模型的图片内容。

## 4. 接口设计

### 4.1 上传附件

`POST /api/conversations/{conversationId}/attachments`

- 请求类型：`multipart/form-data`。
- 文件字段：`image`。
- 一次上传一个文件。
- 响应沿用项目现有 `Result` 包装。

响应 `data` 示例：

```json
{
  "id": "attachment-id",
  "name": "架构图.png",
  "contentType": "image/png",
  "size": 1258300,
  "status": "UPLOADED",
  "previewUrl": "/api/conversations/conversation-id/attachments/attachment-id",
  "expiresAt": 1791712800000
}
```

规则：

- 上传前确认会话存在，并检查访问权限。
- 上传成功不创建用户消息，也不触发模型调用。
- 文件名仅用于展示，不作为存储路径或附件标识。
- 返回附件 ID 和元信息，不返回 Base64。
- `previewUrl` 只用于浏览器查看，不直接传给模型。

### 4.2 发送聊天消息

沿用 `POST /api/conversations/{conversationId}/messages/stream`。

扩展请求：

```json
{
  "content": "请分析这张架构图的问题",
  "attachmentIds": ["attachment-id"]
}
```

兼容与校验规则：

- 原有 `{ "content": "你好" }` 请求继续有效。
- `attachmentIds` 未传或为空时按纯文本处理。
- 文本和附件不能同时为空。
- 保持现有文本长度限制；一期附件列表最多一个元素。
- 附件必须存在、未过期、属于当前会话且尚未绑定消息。
- 不接受前端传入任意图片 URL、Base64 或其他会话的附件 ID。
- 模型能力及历史图片预算校验失败时，不保存新的用户消息。

新增 SSE `accepted` 事件，在用户消息保存和附件绑定成功后发送：

```text
event: accepted
data: {"userMessageId":"message-id","attachmentIds":["attachment-id"]}
```

原有 `message`、`done`、`error` 事件保留。前端收到 `accepted` 后，用服务端消息 ID 替换临时消息 ID。所有必要的客户端校验失败应在建立 SSE 响应前返回明确错误；模型运行阶段失败继续使用 `error` 事件。

### 4.3 读取和删除附件

| 接口 | 用途 |
| --- | --- |
| GET /api/conversations/{id}/attachments/{attachmentId} | 返回图片二进制，用于草稿及历史预览 |
| DELETE /api/conversations/{id}/attachments/{attachmentId} | 删除未绑定消息的附件 |

读取和删除都校验会话及附件归属，并执行访问权限检查。读取响应返回校验后的图片类型和 `X-Content-Type-Options: nosniff`。

已绑定消息的附件不能单独删除，避免破坏历史问答和重新生成；由清空或删除会话统一清理。

### 4.4 失败后的回复重试

已有助手回复时，继续使用现有重新生成接口。

若用户消息已保存但没有助手回复，新增重试接口：

`POST /api/conversations/{id}/messages/{userMessageId}/retry/stream`

- 仅允许重试当前会话最后一条尚无助手回复的用户消息。
- 基于已保存的用户图文消息调用模型，不追加用户消息，不重复绑定附件。
- 同一会话已有生成任务时拒绝并发重试。
- 若已有部分助手回复，先获取其服务端消息 ID，再使用现有重新生成接口。

## 5. 消息结构

保留 `ConversationMessage.content` 为纯文本，新增 `attachments` 元信息列表。

```json
{
  "id": "message-id",
  "role": "user",
  "content": "这张图有哪些问题？",
  "attachments": [
    {
      "id": "attachment-id",
      "name": "架构图.png",
      "contentType": "image/png",
      "size": 1258300,
      "previewUrl": "/api/conversations/conversation-id/attachments/attachment-id"
    }
  ]
}
```

- `ConversationChatRequest` 增加 `attachmentIds`，文本和附件至少有一项。
- 无附件的旧消息返回空列表，前端也兼容未提供 `attachments` 的响应。
- 内部模型消息增加仅由服务端设置的结构化图片字段；通用聊天接口不开放未经附件校验的图片输入。
- 历史接口仅返回元信息，不查询或返回图片二进制及 Base64。
- 复制消息仍只复制文字；纯图片消息不展示文字复制按钮。
- 首条消息为纯图片时，以“图片：文件名”生成标题，应用现有标题长度限制。

## 6. 存储设计

### 6.1 存储决策

一期推荐使用现有 MySQL，新增独立附件表保存元信息及二进制图片，不引入对象存储服务或文件目录配置。

取舍：减少新增基础设施和部署配置，但增加数据库容量、备份及读写成本。图片量增长后，可保持附件 API 不变，仅迁移底层内容存储。

实施前需确认新增数据库表，并检查 multipart、反向代理和数据库包大小等实际限制是否支持 10 MB 文件。若需要调整配置，应先说明原因和影响，不能直接覆盖现有配置改动。

### 6.2 附件表

建议新增 `ai_conversation_attachment`：

| 字段 | 建议类型 | 用途 |
| --- | --- | --- |
| id | VARCHAR(64) | 附件主键 |
| conversation_id | VARCHAR(64) | 所属会话 |
| message_id | VARCHAR(64)，可空 | 所属用户消息，未发送时为空 |
| original_name | VARCHAR(255) | 展示文件名 |
| content_type | VARCHAR(64) | 校验后的图片类型 |
| size_bytes | BIGINT | 图片大小 |
| content | LONGBLOB | 原始图片二进制 |
| created_at | BIGINT | 上传时间戳 |
| expires_at | BIGINT，可空 | 未绑定附件的过期时间，绑定后为空 |

建立会话、消息和过期清理相关索引。`UPLOADED`、`BOUND` 状态由消息关联和过期字段推导，不额外维护重复状态字段。

元信息查询显式选择必要字段，不能通过 `SELECT *` 把图片内容加载进会话列表。

### 6.3 与现有会话保存的兼容

- 附件不通过消息删除级联清理，避免 `MysqlConversationStore.save()` 重写消息时误删图片。
- 普通会话保存不修改已绑定附件。
- 历史加载时，根据会话和消息 ID 批量关联附件元信息，避免逐条查询。
- 用户消息保存和附件绑定在同一事务内完成。
- 清空或删除会话时，在对应事务内显式删除附件。
- MySQL 存储增加附件实现；内存模式增加对应实现并扩展消息复制逻辑。
- 内存模式服务重启后丢失数据的行为保持一致，不承诺跨重启持久化。

## 7. 附件生命周期与事务

```text
本地文件 → 上传成功：未绑定附件 → 发送成功：绑定用户消息
                                    → 清空或删除会话：删除附件

未绑定附件 → 用户移除：删除
           → 超过 24 小时：过期清理
```

发送处理顺序：

1. 校验文本、附件数量、模型能力和图文历史预算。
2. 校验附件存在、未过期、属于当前会话且未绑定。
3. 在同一事务中保存用户消息，并通过条件更新绑定附件。
4. 提交事务后发送 `accepted` 事件。
5. 在数据库事务之外执行模型调用和 SSE 输出。
6. 按现有方式保存助手回复。

条件绑定和过期清理需避免竞态：绑定只接受未过期、未绑定附件；清理只删除已经过期且仍未绑定的附件。绑定失败时回滚用户消息保存。

模型失败或停止生成不解除附件绑定，也不删除已经保存的用户消息。不得让数据库事务持续等待模型响应。

## 8. 前端交互

保持现有输入框布局，增加图片按钮、隐藏文件输入和附件预览区域。

```text
┌──────────────────────────────────────────┐
│ [图片预览] 架构图.png · 1.2 MB     [移除] │
│                                          │
│ 输入问题，也可以仅发送图片……              │
│                                          │
│ [添加图片] [模型] [深度思考]        [发送] │
└──────────────────────────────────────────┘
```

- 文件选择、粘贴和拖拽统一走附件校验及预览逻辑；普通文本粘贴保持原行为。
- 一期已有图片时，再选择图片应明确提示替换，不默默覆盖。
- 点击发送后才上传，减少用户选图后取消产生的孤立附件。
- 上传成功后缓存附件 ID；聊天提交失败时不重复上传。
- 文本或图片至少有一项，且没有上传或生成任务时，允许发送。
- 上传和生成期间禁用相关输入、发送和模型切换操作，防止重复提交。
- 图片、文字及上传结果绑定会话 ID；切换会话不串用草稿，异步结果也按原会话归属处理。
- 收到 `accepted` 后清空已发送草稿，展示服务端确认的用户消息。
- 历史消息展示图片和文字，点击图片查看大图，主题和移动端样式沿用现有设计。
- 清理被移除附件及不再使用的本地预览资源，避免长期占用浏览器内存。

### 8.1 失败处理

| 场景 | 处理 |
| --- | --- |
| 前端文件校验失败 | 明确提示原因，不发起上传 |
| 上传失败 | 保留图片和文字，允许重新上传 |
| 聊天提交校验失败 | 保留草稿和附件 ID，修正后提交 |
| 附件已过期 | 提示重新上传；本地文件仍在时允许恢复 |
| 网络中断，发送结果不明确 | 重新读取会话，根据附件绑定结果确认是否已保存，不直接重复提交 |
| 用户消息已保存，模型失败 | 保留图文消息，通过重试或重新生成调用模型 |
| 用户停止生成 | 保留图文消息和已有助手回复 |
| 图片读取失败 | 展示失败占位及重试入口，不影响其他消息显示 |

## 9. 多模态调用与模型能力

- 扩展 `AiChatService` 的消息转换逻辑，不直接使用同步单轮 `chatWithImage()` 替代流式聊天。
- 普通消息保持文本消息；带附件的用户消息构造 `text + image_url` 内容块。
- 后端读取图片并构造 data URL，模型不需要访问本应用的图片读取地址。
- 后续追问和重新生成都重新组装相应历史图片，不只保留首次识别结果。
- 纯图片消息不能被现有空文本过滤逻辑丢弃。
- 设置累计图片数量、大小和模型上下文保护上限；实际限制取应用保护上限与已确认上游限制中更严格者。
- 超限时明确提示开启新会话，不静默裁剪或丢弃图片。

建议由后端提供现有模型的能力信息，例如 `supportsImageInput`，前端用于展示，后端负责最终校验。不根据厂商或模型名称推断能力，未知模型默认不支持图片。

当前草稿或实际发送的历史上下文包含图片时，切换到不支持图片的模型应提示并阻止发送，不能静默丢弃图片或自动更换模型。

实施前需要确认实际配置的上游模型支持图片输入，并验证现有 ai4j 版本在流式请求中的多模态序列化行为。不因本功能主动升级依赖；若确有必要新增依赖，先说明原因和影响。

## 10. 安全与隐私

- 使用格式白名单，联合检查文件大小、MIME、文件签名及图片有效性，不能只信任扩展名和客户端 MIME。
- 限制图片尺寸、解码资源、上传频率和未绑定附件总量，避免资源消耗失控。
- 使用服务端生成的附件 ID，文件名仅用于展示，并进行长度限制和安全转义。
- 上传、读取、删除、绑定都检查会话及附件归属，并执行访问权限校验。
- 不接受客户端传入任意远程图片 URL，不增加服务端远程图片抓取能力。
- 不在日志中记录图片内容、Base64、完整模型请求、密钥或凭据。
- 明确提示用户图片会发送至当前模型服务商。
- 当前会话模型未体现用户归属。会话 ID 和附件 ID 不是授权凭据；若面向多用户上线，需先补齐会话访问权限，不能把附件归属检查视为用户隔离。

## 12. 验收与验证

功能验收重点：

- 纯文本请求及现有 SSE 行为不回归。
- 图文、纯图片可以发送，刷新后图片可以回显。
- 追问和重新生成包含相应历史图片。
- 会话切换不串用草稿，网络失败不重复创建用户消息。
- 非法文件、过期附件、跨会话附件和重复绑定被明确拒绝。
- 不支持图片的模型给出明确提示，不静默丢弃图片。
- 普通会话保存不误删图片；清空、删除及过期清理正确执行。
- MySQL 和内存模式都支持图片输入，内存模式复制附件元信息正确。

本次仅输出设计，不实施代码、数据库或配置变更，不运行编译和测试。

后续实施默认只使用本机 JDK 8，按项目约定验证受影响模块编译，不主动运行测试。编译通过不能替代模型、SSE、事务并发和浏览器交互验收；未执行的检查及实际模型能力需要明确记录。
